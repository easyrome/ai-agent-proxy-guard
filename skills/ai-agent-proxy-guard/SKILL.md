# AI Agent 代理断线保护

保护对象是用户指定的应用及代它联网的组件。约束写成一句可测试的话，例如「桌面应用和 CLI 只可经专用本机代理访问公网；该上游失效时，两者的新请求失败，普通浏览器保留原有分流」。把批准的备用出口、需要的局域网服务和浏览器配置档写清楚。默认以单一批准出口为限。

## 1. 先识别真实路径

- 记录系统、客户端与实际核心版本、运行模式和配置来源。区分桌面主程序、网络服务子进程、CLI、共享解释器、浏览器、容器及系统解析服务。由谁打开 socket，保护和取证就要覆盖谁。
- 分别画出两段路径：应用到本机代理或 TUN，以及代理核心到上游。查实际监听者、路由、DNS、代理旁路和规则命中。HTTP、SOCKS、系统代理、TUN 可能同时存在并使用不同核心。节点名称、托盘开关和地理位置不能识别实际出口。
- 只读任务止于观察与缺口。在只有一条管理通道或当前会话依赖该代理时，先做离线准备。配置变更前保存有效配置和持久配置、数据库一致性副本、相关策略及独立恢复步骤；故障演练需要可用的本地控制或带外恢复。

## 2. 建立两道约束

1. **代理端分流。** 受保护进程、专用入站或目标域名命中固定出口，组内排除直连和未批准的备用节点。即使目标是 IP、未知域名或被归入国内，也不能让已识别的受保护请求滑入普通直连规则。按 [分流、DNS 与 WebRTC](references/routing-dns-webrtc.md) 配置代理及解析器。
2. **客户端系统边界。** 代理完全退出后仍应能强制执行。显式代理架构可让应用只接触受信任的本机中继；TUN 架构要限制应用在物理出口的直连，同时允许核心连接节点。覆盖 IPv4/IPv6、TCP/UDP、重启、版本变更及新接口。仅靠环境变量、域名名单或失联后才运行的监控有空窗。

Windows 原生程序按 [系统级保护与 Windows 示例](references/system-enforcement.md) 操作。该页也给出移动端和隔离运行环境的适用条件。无法建立或核实系统边界时，报告具体缺口，把严格断线保护记为未验证；有明确泄露则记失败。

## 3. 用真实请求验收

按 [故障与恢复验收](references/fault-tests.md) 分开测试上游失联、整套代理退出和只停 TUN。先证明故障真的发生，再在故障窗口内发出全新请求。只在已授权演练的范围内注入故障，优先使用可控的隔离副本和自有测试端点；生产设备的结论需要对应设备上的证据。

Windows 可用 [只读连接采样脚本](scripts/observe-windows.ps1) 辅助记录已识别进程的 TCP 目标类别及 UDP 绑定数。它不会探测公网。结合系统拦截事件、出口日志或物理接口上的取证判定路径。

## 4. 交付可复核的结论

按应用身份、场景、地址族分别报告 **通过 / 失败 / 未验证 / 不适用**。至少列出分流、系统直连限制、DNS、WebRTC、IPv6、断线与恢复；说明哪些是真实应用结果，哪些只是配置或采样。明确测试版本、时间窗、未覆盖的出口和离线恢复方法。

详细证据留在用户本地。对外分享时用「批准出口 A」「物理接口 B」「协议与规则编号」代替真实地址、节点、订阅、账号和完整日志。
