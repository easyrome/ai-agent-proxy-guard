# AI Agent VPS 部署与稳定性

把用户认可的 VPS 配成可维护的代理出口：可恢复的 SSH、经过验证的业务入口、最小权限服务，以及有前后对照的性能调整。基线来自一台德国 VPS 的实际运维经验；地理位置本身不保证低延迟。

## 默认方案与适用条件

| 项目 | 新机器的起点 |
| --- | --- |
| 系统 | 官方 Ubuntu Server 24.04 LTS 镜像，安装安全更新；按硬件选择 amd64 或 arm64。已有受支持系统优先保留。 |
| 代理 | 官方 Xray，VLESS + REALITY + Vision，RAW/TCP 传输。部署时核对稳定版本及客户端兼容性。 |
| 业务端口 | TCP 443；发现已占用或路径异常时先查原因，再比较其他允许的端口。 |
| 管理端口 | 使用现场实际 SSH 端口。新系统通常是 TCP 22；高位端口主要减少扫描噪声。 |
| 访问保护 | SSH 密钥登录、UFW 或现有防火墙、SSH 专用 Fail2ban、自动安全更新。 |
| 网络起点 | 发行版内核提供的 BBR + fq，核对实际队列和新连接行为后保留；不承诺固定倍数提速。 |

这套用户态代理不需要开启 IP forwarding，不需要图形桌面、容器平台或管理面板。小流量可从 1 vCPU / 1 GiB 内存起步，容量是否足够由并发、CPU steal、内存、带宽和流量额度决定。

## 工作顺序

1. **确认对象与现状。** 从当前连接和配置取得系统、架构、实际 SSH 监听、代理版本、服务用户、现有业务和防火墙；不把历史端口或旧 IP 当现状。确认用户要新部署、迁移、升级还是诊断。已有出口选择继续有效。
2. **保存可恢复的基线。** 先验证云控制台或另一条恢复路径，保留原 SSH 会话和独立的新密钥会话。备份本次会修改的文件、权限及运行值。变更登录、防火墙或路由前按 [验证与恢复](references/verification-recovery.md) 准备限时回滚。
3. **部署最小服务。** 按 [部署步骤](references/deployment.md) 安装软件、生成本机独有凭据、填充 [服务端模板](assets/server-config.example.json)，验证配置后再切换。已有系统只应用必要差异。
4. **测量后调整。** 按 [性能与端口](references/performance.md) 建立同目标、同路径、同时间段的基线。每次只改变一个主要因素，记录成功数、失败数、p50/p95 及样本量。速度优先级不能取消认证或客户端的断线保护。
5. **用真实入口验收。** 除语法检查，还要完成新 SSH 登录、实际代理请求、出口确认、服务重启后的新连接和规则持久性检查。重启整机仅在任务范围和维护窗口允许时执行，否则写 `reboot_unverified`。

## 易误判的地方

- TCP 443 可连接只证明端口可达；必须验证 REALITY 握手、认证、目标 HTTPS 和真实应用请求。
- BBR 控制发送端的拥塞行为。服务器启用 BBR 无法保证客户端到服务器的上传链路或跨境路由变快。
- 大缓冲、改端口、增加重试、修改测速超时都需要对应瓶颈证据。一次下载或累计重传计数不能证明改善或丢包率。
- 服务端成功不等于客户端不会泄漏 IP。仍要限制本地应用的直连、备用出口、DNS、WebRTC 和 IPv6；可结合同仓库的 `ai-agent-proxy-guard`，也可使用现场已有的等效保护。
- REALITY 对未通过认证的 TLS 连接可能回落到配置的 `target`；这与 AI Agent 在本机绕过代理直连是不同路径，分别检查。
- 公共报告只包含匿名化结论和示例；真实 IP、密钥、UUID、订阅链接、管理端口、会话日志留在用户控制的私有位置。

## 交付

给出系统和软件版本、实际生效的端口与服务身份、修改内容和备份位置、测试范围、前后数据及剩余缺口。登录材料通过用户认可的私密渠道交付。保留未知项：`config_validated`、`client_verified`、`recovery_verified` 和 `reboot_unverified` 等状态各指自己的证据，不能相互代替。
