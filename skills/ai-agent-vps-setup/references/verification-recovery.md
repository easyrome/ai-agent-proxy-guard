# 验证与恢复

## 变更前的恢复条件

高风险项包括 SSH 认证/端口、防火墙默认策略、路由、网卡队列及服务升级。先确认现有授权、恢复通道和影响窗口；已有授权足够时继续执行，缺的是具体访问资料才向用户询问。

保存本次将修改的文件及不存在状态、属主和权限，以及相关 sysctl 旧运行值、服务 unit、监听和生效规则。备份在用户私有位置，以日期和变更 ID 命名。不要把含密钥的快照提交到公共仓库。

需要断联保护时，依据这份快照准备只恢复本次差异的脚本，并用 systemd 的限时任务或云控制台执行。`systemd-run --on-active=10m --unit=agent-change-rollback /root/本次恢复脚本` 是机制示例，必须先写好脚本并验证目标路径；任务本身存在不代表恢复脚本可靠。暂存 timer 不能保护整机重启后的窗口，重启测试须依赖经验证的控制台或持久恢复机制。

恢复脚本应分别处理 SSH、防火墙、服务文件和 sysctl：某个键恢复失败不能让后续 SSH 恢复被 `set -e` 提前跳过。恢复前比较本次写入后的哈希或规则 ID，发现后续他人改动就保留差异并使用控制台处理，不覆盖新的配置。仅撤回本次添加的规则，避免清空整套防火墙或导入陈旧全量快照。

## 最小验收矩阵

| 证据 | 通过标准 |
| --- | --- |
| 配置 | 当前二进制版本明确；`xray run -test` 成功；专用服务用户可读取配置；无模板占位符。 |
| SSH | 保留旧会话的同时，新独立密钥会话成功；需要的 sudo 可用；`sshd -T -C` 和实际监听匹配。 |
| 服务 | 正确 unit/配置/用户在运行；能力集合与路径权限符合方案；无重启循环或新增错误。 |
| 网络入口 | 云与主机规则匹配；只开放已决定的业务/管理入口；IPv4、IPv6 各自有结论。 |
| 新增或迁移端口 | 服务监听、认证、客户端专用出站、DNS 出站和持久模板一致；旧入口/临时入口保留或撤销有明确记录；所有批准路径都纳入故障验收。 |
| 原有业务 | 同一入口复测变更前的网站或其他服务，状态符合原基线；新增代理不能占用原服务端口或破坏其访问。 |
| 客户端 | 从用户实际网络经指定入口完成认证、目标 TLS 和新 HTTPS 请求；真实 AI Agent 请求也成功。 |
| 出口 | 通过用户认可的检查端点确认实际出口；不因 IPv4 正常就推断 IPv6 一样。 |
| DNS | 本地代理、TUN 和浏览器各按实际使用方式取证；无证据的模式保持未验证。 |
| SSH 封禁 | 配置测试及 jail 状态正常；必要时以保留的测试地址做 ban/unban 并查实际规则，清除测试状态。 |
| 性能 | 同目标、同路径、样本量、超时/失败、p50/p95 与前后变化都有记录；小文件速率不称为线路上限。 |
| 恢复 | 计划内服务重启后新连接成功；本次回滚目标正确，临时任务和规则的保留/清理状态明确。 |
| 持久性 | 有重启授权和恢复手段时验证重启后的 SSH、代理、规则与新请求；否则 `reboot_unverified`。 |

必要的服务重启会断开部分活动请求，选定影响窗口，不把本次“写技能”的请求当成操作读者生产机的授权。核心验收失败时不要取消恢复保护；先执行有范围的恢复并确认新 SSH 和代理请求。

## 收尾和交付

验收通过后明确取消本次 rollback timer，核对 timer/service 已停止，清理本次测试用 ban、临时端口和诊断服务。保留原有安全规则；定时恢复脚本不得在后来无人知情时撤销已验收配置。

对外报告记录匿名化软件版本、配置选择、测试方法和范围。私密交付记录实际地址、端口、连接材料、备份位置和恢复命令。分开说明：

- 已验证的当前行为。
- 仅通过语法或离线测试的部分。
- 需要真实客户端、特定地址族、特定网络或重启才能验证的部分。

服务器运维完成后，如果目标还包括防 IP 泄漏，继续做客户端断线保护：上游失联、代理核心退出、仅 TUN 停止分别测试。不要把服务自动重启或端口重新监听当成 fail-closed 的证据。
