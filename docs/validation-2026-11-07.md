# 2026-11-07 现场验证摘要

这是维护者对本地既有实测证据的脱敏整理，不是公开 CI 或其他机器的验收结果。原始日志、地址、账号、真实域名、策略身份、浏览器配置档及配置备份仅保留在本地；公开摘要不能替代读者对自己设备的验证。本次发布更新文档，没有再次中断生产网络。

## 防护变更与端口

- 受保护进程/域名和专用 DNS 优先匹配固定出站，早于普通分流及模式切换；固定出站只有批准出口 A，没有直连或其他节点回退。GUI 持久模板与 Xray、sing-box 生成配置均核对。
- 补充受保护域名的 NRPT、浏览器 WebRTC URL 策略及稳定应用包身份的系统阻断规则。域名后缀与第三方精确域名分别维护；真实域名不在公共仓库分发。进程查找失败、共享解释器和未知子进程不自动归入已保护范围。
- 日常浏览器固定本机代理，禁用其绕过系统路径的 DoH 配置，并核对实际加载的策略。故障期间同一浏览器的其他公网网站也可能不可用。
- 本次固定 VPS 业务仍为 TCP 443；已有本机入口示例为 10808/10814。没有证据表明本轮新增了德国 VPS 业务端口。隔离核心使用运行时分配的临时回环端口，测试结束后清理。角色与变更方法见 [端口说明](../skills/ai-agent-vps-setup/references/ports.md)。

## 结果与适用范围

| 场景 | 实际观察 | 结论边界 |
| --- | --- | --- |
| 隔离配置与锁定出口 | Xray 路由模式、sing-box Rule/Global/Direct 对照中，36/36 负向请求失败，逐项关联锁定路由和故障端点；4/4 出口回显、8/8 普通 HTTPS 对照通过。 | 这是非 TUN 隔离副本验收，不等于生产断线或真实应用完成全部测试。 |
| 隔离正常传输 | 正常联网时 24 个受保护目标请求中 22 个取得 HTTP 应答；同一根域名的两次正常访问未成功。 | 该域名路由和负向失败已观察，正常可达性仍未验证；403/404/426 等只代表收到服务器响应。 |
| 生产整套代理退出，隔离浏览器 | 10 个连续状态样本确认管理器、核心、TUN、相关路由及本机代理入口退出；隔离 Chrome 新请求出现代理连接失败，真实原生 CLI 的直连尝试有 5 条原始 WFP Drop。 | 浏览器为未登录的隔离 headless 配置档，不代表日常 profile；CLI 的丢弃事件不能归给 Chrome，具体持久规则归因仍有缺口。 |
| 生产仅停 TUN，隔离浏览器 | 12 个连续状态样本确认 TUN 及其入口退出，管理器与 Xray 的原进程身份保持，本机代理继续可用；Chrome 的新 HTTPS 及批准出口回显正常，同一 CLI 直连尝试有 5 条 WFP Drop。 | 经保留的批准代理继续联网符合要求；不能将该结果扩展为日常浏览器也完成了 TUN-only 测试。 |
| 日常浏览器整套代理退出 | 在稳定故障窗口内，六个 origin 的 43 次新 HTTP 请求均失败；物理网络的独立对照仍可用。恢复后重新发起请求并取得应答。 | 当前实际日常 profile、当前配置和本次窗口的行为证据；没有推广到所有域名、应用或未来版本。 |
| 日常浏览器 WebRTC | 七个 origin 严格位于故障窗口内的 51 次采样均完成且无 ICE 候选。 | 现场既有 WebRTC 扩展与策略共同作用，不能单独归因于某个策略；零候选不等于连续抓包无泄漏。 |
| API origin 补测 | 正常页内 fetch 被 CSP 拒绝，改用允许的顶层导航；两次故障导航显示 `ERR_PROXY_CONNECTION_FAILED`，故障前后全新导航经本机代理回显批准出口。另有故障内 5 次完成的 WebRTC 零候选样本。 | 可观察行为通过；时序由本地定时器、唯一请求标记和实际错误文档事件有界关联。原始请求开始/失败事件因缓冲淘汰缺失，完整原始逐请求链仍 `unverified`。 |
| 原生应用阻断证据 | 故障期间关联真实受保护 CLI 进程的 WFP Drop，独立直连与 STUN 对照可用；补测事件内含 Block 和策略来源。 | 事后过滤器 ID 与快照的关联仍有缺口；不把 CLI 证据归给桌面主程序或浏览器。 |
| 自动恢复和清理 | 配置与相关策略前后核对一致，独立数据库备份完整性通过，正式监听与 TUN/代理 HTTPS 恢复；控制器、watchdog 及测试页已清理。 | 备份哈希和恢复成功各有证据，不声称运行中数据库逐字节不变；救援时限不是联网恢复耗时保证。 |

第一轮 API 补测的导航实际晚于恢复开始，已保留为无效故障样本，不计入通过。后续补测使用故障前登记的本地定时动作，避免断网阻塞控制通道。没有关闭 CSP、证书验证或防火墙来制造成功基线。

生产两场景的隔离浏览器各完成六个 HTTPS origin 的 WebRTC 零候选采样，但该轮 API origin 未获得可执行文档，仍未验证。两个原生 IPv4 STUN 阳性对照可用；浏览器普通对照的 STUN 超时，因此不能单独归因于 URL 策略。两场景恢复均完成真实 HTTPS、出口、端口归属与配置核对，测试与看护进程已退出。之后的日常 profile 和 API 补测使用各自独立证据，不混并样本。

## 仍未验证

- 本轮公网 IPv6、新增网卡、跨网络切换、冷启动及任意未来版本。
- 桌面主程序、虚拟机、共享解释器和任意派生子进程；日常浏览器 profile 的仅停 TUN 模式仍未实测，已完成的是上述隔离浏览器与原生 CLI 的该场景。
- 未登记的第三方域名、浏览器任意裸 IP 与采样间隙的所有流量。
- API 两次故障请求完整的原始起止事件链，以及工具启动链与原生策略视图差异的底层原因。

工具进程曾看到旧注册表策略，但同用户原生只读进程、日常浏览器策略页面与实际行为一致。修正的是诊断路径，没有据此重写已正确生效的策略，也没有把原因未经证明地写成缓存或系统虚拟化。

## 在其他机器复现

按 [故障与恢复验收](../skills/ai-agent-proxy-guard/references/fault-tests.md) 重新识别进程、profile、批准出口、监听端口和模式，保存本机备份并验证独立恢复。先取成功的网络基线，再确认稳定故障窗口，记录请求与恢复时序；时序不完整或正常基线本来失败的用例保持未验证。不要复制这里的样本数或结论当作自己的验收。
